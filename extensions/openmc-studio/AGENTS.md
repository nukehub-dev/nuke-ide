# OpenMC Studio

## Purpose

No-code graphical workspace for OpenMC Monte Carlo neutron transport simulations inside NukeIDE: simulation dashboard, CSG builder, DAGMC editor, tally configurator, optimization framework, simulation comparison, XML round-trip, project management, CAD import, and a simulation runner.

## Ownership

All files under `extensions/openmc-studio/` except generated artifacts (`lib/`, `node_modules/`, `*.tsbuildinfo`, `__pycache__`).

## Local Contracts

- TypeScript side follows `extensions/AGENTS.md`: `src/browser/` (React widgets per feature: csg-builder, dagmc-editor, native-plotting, optimization, simulation-comparison, simulation-dashboard, tally-configurator, volume-calc), `src/common/`, `src/node/`; widget CSS is copied to `lib/` by the `copy-css` build step.
- Python backend lives in `python/` and is **not pip-installed**; the IDE spawns it as a subprocess:
  - `python/cad_conversion/` — CAD→DAGMC/CSG conversion pipeline package. The DAGMC fallback (`nurbs_handler.py`) auto-creates a `mat:graveyard` bounding volume when the input does not already appear to contain one; detection uses STEP/IGES product names and a volume/bbox heuristic, existing graveyards are re-tagged `mat:graveyard`, and creation can be disabled with `--no-graveyard` / `addGraveyard: false`.
  - `python/cad_importer.py`, `python/dagmc_editor_service.py`, `python/dagmc_info.py` — CAD/DAGMC services. `dagmc_editor_service.py` exposes `detect_graveyard`, `tag_graveyard`, and `create_graveyard_box` for existing `.h5m` files: detection scans volume bounding boxes for an enclosing volume and reports whether a graveyard can be created, `create_graveyard_box` builds a new axis-aligned bounding cube tagged `mat:graveyard` (preferred), and `tag_graveyard` re-tags an existing enclosing volume as `mat:graveyard` (secondary/unsafe); the DAGMC editor widget surfaces the create action as a primary banner button with the re-tag action as a secondary warning.
  - `python/run_depletion.py`, `python/run_optimization.py`, `python/run_keff_search.py`, `python/build_chain.py` — run drivers. `run_depletion.py` supports coupled and independent operators, `get_microxs_and_flux` generation, transfer rates, custom fission Q, and diff burnable mats. `run_keff_search.py` wraps `openmc.search_for_keff` (criticality search).
  - `python/generate_mgxs_library.py` — fine-grained MGXS generation with the raw `openmc.mgxs.Library` API (the machinery `convert_to_multigroup` wraps, model.py:1944): user-chosen XS types (validated vs `MGXS_TYPES`), domain type/IDs, by-nuclide, Legendre order, estimator; auto-appends `consistent nu-scatter matrix` + `multiplicity matrix` when missing (XSdata conversion requires them, library.py get_xsdata ~1197-1250). Driven by the MGXS Generator window's Library (manual) mode. NOTE: `model.run` leaves `model.xml` in the working dir, which shadows patched settings/materials on later binary runs — delete it before multigroup runs.
  - `python/build_chain.py` — depletion chain builder, two modes: `--from-chain` (subset an existing chain XML; closure over decay/reaction targets, fission-yield products, AND FPY-borrow parents — all required by the depletion operator, so fissile subsets legitimately stay large) and `--from-endf` (`Chain.from_endf` reads ENDF TEXT sub-libraries decay//nfy//neutron/ only — incident HDF5 like U235.h5 carries no decay/FPY data and CANNOT build chains; accepts both `neutron/` (B-VIII) and `neutrons/` (B-VII) layouts). UI lives in the Depletion tab (Custom Chain Builder section); result offers Use as Depletion Chain writing `depletion.chainFile`.
  - `python/run_volume_calc.py`, `python/generate_plots.py` — volume calculation and native plotting jobs (stdout-JSON protocol: progress on stderr, one final JSON object on stdout).
  - `python/ncrystal_import.py`, `python/generate_mgxs.py` — NCrystal material import and MGXS library generation one-shot jobs (same stdout-JSON protocol). `generate_mgxs.py` guards MG settings / macroscopic materials BEFORE the openmc import (`read_model_compatibility`, stdlib ET → exit 1 + clean JSON): MGXS generation is a CE per-nuclide workflow, and on DAGMC/C-API paths `model.run` executes IN-PROCESS via `openmc.lib` — a libopenmc `fatal_error` there is a C-level `std::exit(-1)` (exit 255) that bypasses Python exceptions, so NO final JSON is printed and openmc's own log lines pollute stdout. Correspondingly, `executePythonScriptJson` (`openmc-runner-service.ts`) scans stdout BACKWARDS for the last JSON-parsing line and, finding none, reports `exit code N` + the stderr/stdout tail (never 'Failed to parse script output: <log line>'). The MGXS Generator window disables Generate with the same guidance when the project is MG/macroscopic.
  - `python/sync_dagmc_depletion.py` — DAGMC sync-for-depletion job (init_lib → sync_dagmc_universes → finalize_lib; rewrites geometry.xml with per-cell material overrides, never the .h5m). `dagmc_editor_service.py` also has a `replace_material` (by-name) subcommand; auto_geom_ids/auto_mat_ids live on `DAGMCInfo` and are emitted on the `<dagmc_universe>` element.
  - `python/statepoint_reader.py` — statepoint parsing/comparison.
  - Phase 5 adds `python/common/` (shared stdout-JSON envelope), `python/h5_readers/` (HDF5 readers), and re-adds `generate_mgxs.py` (previously removed — restored in W8 as a `convert_to_multigroup` wrapper).
- `src/browser/contributions/openmc-tools-contribution.ts` exposes OpenMC Studio commands in the Nuke Tools sidebar (`nuke-core`), organized into Project, Geometry, Simulation, XML Configuration, Advanced, and Environment. Items that require an opened project are disabled until `OpenMCStateManager.projectPath` is set.
- Python runtime dependencies (openmc, numpy, gmsh/CadQuery/`OCP`, pythonocc-core/`OCC`, pydagmc/moab) are provided by the `ide` conda environment — see `applications/docker/environment.yml` and `docs/installation.md`. Tests must not require them: the test environment only has `pytest` + `numpy`, so guard heavy imports.
- Simulation/optimization binary resolution (`openmc-runner-service.ts`, `optimization-backend-service.ts`) locates the `openmc` executable in this order: (1) `$OPENMC_ROOT/bin/openmc`, (2) `openmc` resolved on `PATH` (with the selected Python's directory and `$OPENMC_ROOT/bin` prepended), (3) next to the selected Python interpreter, (4) a sibling `bin`/`Scripts` directory. Set `OPENMC_ROOT` or put `openmc` on `PATH` for installs outside the detected Python environment.
- Cross-sections and depletion chain precedence for simulation/optimization runs: (1) explicit preferences (`nuke.openmcCrossSections`, `nuke.openmcChainFile`), (2) `OPENMC_CROSS_SECTIONS` / `OPENMC_CHAIN_FILE` environment variables inherited by the backend process, (3) OpenMC defaults. Preferences override env vars.
- Python package requirements live in `src/common/packages.json` (single source consumed via `src/common/packages.ts`); never inline package lists in services/widgets; `pydagmc`'s installCommand must stay pinned.
- Tests: `tests/python/` runs from the repo root via `yarn test:python`; `conftest.py` puts `python/` on `sys.path` so `cad_conversion` and the top-level service modules are importable.
- E2E tests live in `tests/e2e/` (pytest, driver-level, `@pytest.mark.e2e`, full profile only) and `src/node/e2e/` (vitest, project-level). Conventions: pytest fixtures build tiny models with the openmc API at runtime (3-cell pincell, ~300 particles, 12 batches — seconds per run); shared helpers live in `e2e_helpers.py` (NEVER `from conftest import ...` — conftest module names collide across test dirs). Path policy: no machine-specific defaults — cross sections come from `OPENMC_CROSS_SECTIONS`, the depletion chain from `NUKE_E2E_CHAIN`, ENDF sub-libraries from `NUKE_E2E_ENDF` (ENDF-mode chain-builder e2e only), all optional (tests skip when unset). Pytest e2e files: `test_run_drivers_e2e.py` (CMFD/depletion/keff-search/volume/MGXS/collision-track), `test_dagmc_assets_e2e.py`, `test_generate_plots_e2e.py` (slice/voxel PNG+HDF5 via C++ plot mode, raytrace; `.vti` conversion gated on `vtk`), `test_build_chain_e2e.py` (subset + ENDF chains → real depletion), `test_generate_mgxs_library_e2e.py` (Library mode → mgxs.h5 → real multigroup run). Vitest fixtures are small hand-written `.nuke-openmc` JSON projects under `src/node/e2e/projects/` (reviewable, a few KB — no generated XML in the repo): `pincell-kinetics`, `fixed-source-tracks`, `pincell-depletion`, `pincell-volume`, `dagmc-pincell`, `pincell-cmfd`, `pincell-derivative`, `mesh-source`, `random-ray`, `tokamak-source` (gated on an openmc `TokamakSource` feature probe, 0.15.4+), and `migration-v1.0.0` (real Phase-5-era project proving schema migration); `fuel_pin.h5m` (1.2 MB) is committed at `tests/e2e/assets/`. Vitest e2e files: `project-run.test.ts` (fixtures → XML → real runs; the random-ray project regenerates its multigroup settings.xml through the IDE generator with an explicit `raySource`, covering the version-aware emission — `generate_mgxs.py --random-ray` alone would bypass it via Python-side re-export) and `codegen-run.test.ts` (fixtures → `OpenMCPythonExporter` → generated `model.py` executed with the env python → exported XML run under openmc; the exporter's three browser-only imports are `vi.mock`ed — generation methods are DOM-free, only save/dialog paths use them). ## Work Guidance

- Keep the graphical model and OpenMC XML in sync through the existing round-trip modules; do not add one-way generators.
- Surface boundary contract (fixed after e2e caught vacuum-everywhere emission): `generateSurfaceElement` emits a `boundary` attribute ONLY when `OpenMCSurface.boundary` is set; unset means OpenMC's transmission default. Interior surfaces must stay unset — only outer-boundary surfaces carry `vacuum`/`reflective`. Cell regions must fully bound the geometry (infinite cylinders need bounding planes), or particles get lost.
- Volume-calc CLI nuance: `--lower-left`/`--upper-right` are passed in equals form (`--lower-left=x,y,z`) because leading minus signs are misread as option flags by argparse; `--domain-type` is required.
- New widget features go in `src/browser/widgets/<feature>/` with their CSS beside the widget; add the CSS file to the copy step if a new directory is introduced.
- `widgets/shared/openmc-widget.css` is the shared design system: generic form/section/button styles scoped `:is(.simulation-dashboard, .openmc-widget)` — standalone widgets opt in by adding `openmc-widget` to their root element (tally-configurator keeps its own scoped sheet instead). It also documents the shared chrome patterns: `.openmc-header` (CSG-style icon + title + subtitle + right-aligned actions + stat counters), `.category-header` + `.count-badge` (collapsible group headers), and top-aligned `.form-row` grids; accent is always `--theia-focusBorder`, all colors are Theia CSS vars.
- Simulation dashboard tabs are `DashboardTabContribution` classes under `src/browser/widgets/simulation-dashboard/tabs/` collected by `DashboardTabRegistry`; add a tab by creating a contribution there and binding it against `DashboardTabContribution` in `openmc-studio-frontend-module.ts`.
- The settings tab is split into collapsible sections (General / Sources / Output / Physics / Advanced / Convergence); section renderers live in `tabs/settings/`.
- The Advanced section (`tabs/settings/advanced-section.tsx`) owns the rarely-changed scalar settings, all optional (undefined = OpenMC default): `eventBased`→`<event_based>`, `probabilityTables`→`<ptables>`, `maxLostParticles`→`<max_lost_particles>`, `relLostParticleRate`→`<rel_max_lost_particles>`, `createFissionNeutrons`/`createDelayedNeutrons`/`delayedPhotonScaling`/`survivalBiasing` (default true), `useDecayPhotons`/`writeInitialSource`/`uniformSourceSampling` (default false), `logGridBins`, `generationsPerBatch`, `maxOrder` (multi-group only), `tabularLegendre {enable, numPoints}`→`<tabular_legendre>`. Element names are verified against settings.py `_create_*_subelement`; new scalar settings belong here, not in one-off sections.
- The Random Ray tab (`tabs/random-ray-tab.tsx`, order 5) owns multi-group mode: `settings.energyMode` ('multigroup' maps to XML `multi-group`), `settings.mgxsLibrary`, and `settings.randomRay` round-trip through settings.xml (`<random_ray>`, `<cross_sections>` deprecated-but-read); `python/generate_mgxs.py` wraps `convert_to_multigroup`/`convert_to_random_ray`, driven by the MGXS Generator window (`widgets/mgxs-generator/`). MGXS LIBRARY CONTRACT: the canonical field is `settings.mgxsLibrary`; legacy pre-1.1.0 projects carry `randomRay.mgxsLibraryPath`. The value may name the `mgxs.h5` FILE (any extension — extension-less HDF5 files exist in the wild) or a DIRECTORY holding it; resolution is fs-aware at the call sites (XML generator stats via fs, the runner via Theia FileService): existing file → as-is, directory/unresolvable → `<dir>/mgxs.h5`. ALL consumers (materials.xml/settings.xml emission, the runner's `OPENMC_MG_CROSS_SECTIONS` env in `simulation-runner.ts` — note the env var OUTRANKS materials.xml, so it must never guess wrong, the tab's picker display) resolve through `resolveMgxsLibrary` (`src/common/mgxs-library.ts`) for the raw value — never read either field directly. The tab picker shows `canonical ?? legacy` and migrates to canonical on first edit (legacy kept). In multi-group mode `generateMaterialsXML` also emits `<cross_sections>` as the FIRST child of `<materials>` (the non-deprecated home; relative paths resolve against the project directory first, then the output directory), and `parseMaterialsXML` reads it back into `settings.mgxsLibrary` when settings.xml lacks one (settings.xml wins on conflict). Weight window generators use the real `<weight_window_generators>` format; meshes referenced by weight windows / the WW generator / UFS MUST be appended as `<mesh>` elements to the settings root (openmc python does this; without it the C++ mesh lookup crashes with `unordered_map::at` during settings reading) — `generateSettingsXML` dedupes via `emittedMeshIds` against the entropy and source-region meshes. FW-CADIS (`method: 'fw_cadis'` + target tallies) is gated on multi-group mode + MGXS library in the VR tab. `adjointSource` (single uniform box; XML accepts a list — UI models the common case) is emitted as `<adjoint_source>` with a nested independent box source. VERSION COMPAT CONTRACT (`OpenMCCompat`, probed at runtime per python env by `OpenMCCompatProbeService` (`src/node/openmc-compat-probe.ts`) — NEVER version parsing; cached per python command, `DEFAULT_OPENMC_COMPAT` = release 0.15.3 on any failure): (1) ray_source — release 0.15.3 reads `<source>` DIRECTLY under `<random_ray>`; post-0.15.3 dev wraps it in `<ray_source>` (its C++ reads only the wrapper). (2) adjoint_source — post-0.15.3 only (release rejects the key); dropped with a warning when unsupported. (3) tokamakSource — `openmc.TokamakSource` exists 0.15.4+ only; tokamak sources are dropped with a warning on older envs, the Settings-tab Tokamak segment is disabled (existing tokamak sources still render, with a hint). (4) s2SampleMethod — random ray `sample_method: 's2'` falls back to 'halton' with a warning when rejected (note: release 0.15.3 ACCEPTS s2 — the probe is a safety net, not an active gate there). The backend RPC `generateXML`/`saveProject` enrich requests through `withOpenMCCompat` (explicit `randomRayCompat` on `XMLGenerationRequest` always wins); `OptimizationBackendService` (sweeps + keff-search) has its own injected `withOpenMCCompat` with the same contract — every `XMLGenerationService.generateXML` call site must enrich or explicitly pass compat, else it defaults to the release profile. The frontend fetches compat via `OpenMCStudioService.getOpenMCCompat()` (cached promise over the `getOpenMCCompat` RPC). `parseSettingsXML` accepts BOTH ray_source forms. `source_region_meshes` format is version-stable (verified on 0.15.3).
- FIXED-SOURCE RANDOM RAY SOURCE CONSTRAINTS: in multi-group fixed-source mode OpenMC requires every source to be constrained to a material, cell, or universe domain (`src/node/openmc-studio-backend-service.ts` `validateState`). The backend errors on unknown domain IDs and warns when a point source lies outside geometry bounds or a box source does not overlap the geometry. The Random Ray tab exposes a **Fixed-Source Domain Constraint** panel that lets users assign constraints per source or to all sources at once, including a heuristic that guesses the plasma/material domain from source spatial bounds. Constraints serialize into each source's `constraints` array and emit as OpenMC `source.domain` objects. Use this to satisfy OpenMC's "constrained to a domain" requirement instead of relying on unconstrained spatial distributions.
- ONE-CLICK CE ↔ MG CONVERSION (P9B): `python/convert_to_multigroup_project.py` runs `generate_mgxs.run_generate_mgxs` (no duplication) then reads mgxs.h5's TOP-LEVEL groups with h5py — material-wise generation names each XS data set after its material, so the mapping is materialName→same name, intersected with materials.xml names (stdlib ET). RPC `convertToMultigroupProject` (runner → `executePythonScriptJson`). The random-ray tab's Multi-Group Conversion section (CE mode only): method/groups/particles/working-dir form → backend generateXML → driver → **Apply Conversion**, which uses the pure logic in `src/common/mg-conversion.ts` (`computeMgConversion`/`computeMgRevert` — matched materials get `macroscopic: {name}`, `densityUnit: 'macro'`, `density: 1.0`; unmatched stay untouched both directions) and stashes the pre-conversion materials + energyMode in `metadata.mgBackup` (optional, version-tolerant, no migration). **Revert to Continuous-Energy** (visible only with a backup) restores both, keeps `mgxsLibrary`, clears the backup. E2E: `src/node/e2e/mg-conversion.test.ts` (fixture → real conversion → real MG run → revert).
- Run readiness and the Setup Checklist are computed by the pure helpers in `src/common/run-readiness.ts` (`computeSetupChecklist` — mirrors the DAGMC-aware materials predicate; `computeReadiness` — materials + geometry + source required, plus the MGXS library in multi-group mode). The simulation tab renders the checklist as a collapsible chip strip (auto-collapsed when ready) and a slim readiness pill; the restart picker is a secondary 'Restart…' button in the run-actions row with a dismissible file chip beside it.
- The source model is a discriminated union (`independent` | `file` | `compiled` | `mesh` | `tokamak`; absent `type` means `independent`) with optional per-source `constraints`; `settings.restartFile` is a run-only option passed to OpenMC as `-r`, never written to settings.xml. When it names a particle restart file (`particle_restart.h5` or the writer's `particle_<batch>_<id>.h5`, parsed by `src/common/particle-restart.ts`), the simulation tab offers track capture (`settings.tracks`/`maxTracks` — note particle-restart mode ignores those XML elements, so the dashboard also passes `-t`; OpenMC auto-derives run mode from the file's `filetype` attr), a preview via OpenerService (nuke-visualizer's particle-restart viewer claims the file), and a post-run 'Open Tracks' action when `tracks.h5`/`tracks_p0.h5` appears in the working directory.
- The `mesh` source variant (`OpenMCMeshSource`, openmc.MeshSource) references a state mesh by `meshId` and holds one independent sub-source per mesh element — this OpenMC version requires exactly `mesh.n_elements` sub-sources (source.py sources setter), so `validateState` enforces the count via `src/common/mesh-utils.ts` (`getMeshElementCount`) and the UI offers a Fill button. Sub-source spatial distributions are ignored by OpenMC at runtime, so the editor only edits strength/energy/particle; total strength is the computed sum of sub-source strengths. The referenced mesh is emitted into settings.xml (settings.py `_create_source_subelement`) and skipped in tallies.xml (OpenMC `mesh_memo` pattern, model.py:714/749); `getSettingsMeshIds` (`xml-generation-service.ts`) is the SINGLE inventory of settings-level mesh emitters (mesh sources, entropy, random ray source-region, VR weight-windows/WWG/UFS — regular meshes only) that tallies.xml skips, so a shared mesh is emitted exactly once (duplicates trigger 'Mesh with ID=N appears in multiple files'); `importXML` merges settings.xml meshes back into `state.meshes`. RANDOM RAY RESTRICTIONS (multi-group): IFP kinetics is CE-only — `validateState` errors, the auto-IFP-tally emission is skipped with a warning, and the Simulation-tab kinetics checkbox is disabled with a hint; tally scores are restricted to {flux, total, fission, nu-fission, kappa-fission, events} (score STRING is 'events' although the C++ error text says "event scores") — `validateState` errors listing offending tallies, and the score selector shows a hint (catalog intentionally NOT filtered).
- The `tokamak` source variant (`OpenMCTokamakSource`, openmc.TokamakSource — versionadded 0.15.4) models Miller flux-surface geometry + an emission profile S(r/a) stored as `{r, s}` pairs (r grid must run 0→1 strictly increasing, S ≥ 0 with one positive, arbitrary units — not normalized) plus a single energy distribution; this class has NO ion-temperature/fuel model, and per-radius energy lists are intentionally not modeled (the optional time distribution IS modeled — see the end of this bullet). XML uses text sub-elements (`major_radius`, `r_over_a`, `emission_density`, …; `vertical_shift` only when nonzero); validation mirrors the class's `_validate` (radii > 0, minor < major, Shafranov < a/2, triangularity ∈ [-1, 1]) via `validateTokamakSource`. The shared energy-type select + param fields helper in `tabs/settings/source-details.tsx` (`renderEnergyFields`) is used by both the tokamak editor and the mesh sub-source editor — extend it for new energy types. ENERGY NOTE: in this OpenMC version `muir(e0, m_rat, kt)` is a FUNCTION returning `Normal` (univariate.py:1243) — there is no muir XML type: muir serializes as `<energy type="normal">` with std_dev=sqrt(2·e0·kt/m_rat), parses back as the `normal` schema type (lossy, documented); legacy `type="muir"` XML is converted to normal on import. TokamakSource `time` (delta/uniform/discrete) round-trips; per-radius energy lists are intentionally NOT modeled.
- Tally scores and filters are data catalogs in `src/common/scores-catalog.ts` and `src/common/filters-catalog.ts` (ground-truthed against the OpenMC clone); the score selector and filter builder render from them — extend the catalogs, not the components. Deprecated upstream moment scores (`scatter-N`) are intentionally excluded; custom integer MTs are accepted. `tallies.xml` round-trips through `importXML` (meshes, all filter types, nuclides, scores).
- Per-tally triggers (`OpenMCTally.triggers`, openmc.Trigger) serialize as `<trigger type threshold [scores] [ignore_zeros]/>` sub-elements of `<tally>` — scores is a space-separated **attribute** (trigger.py `to_xml_element`), empty subset means all of the tally's scores. OpenMC only evaluates triggers when run-level activation is on, so settings.xml/codegen emit `<trigger><active>true</active>` / `settings.trigger_active = True` automatically whenever any tally has triggers; run-level knobs live in `settings.triggers` (`batchInterval`/`maxBatches` → `<batch_interval>`/`<max_batches>`), edited in Settings → Output ('Tally Triggers') and configured per tally in the Tally Configurator's Triggers section (`components/trigger-editor.tsx`).
- Tally derivatives (`OpenMCTally.derivative`, openmc.TallyDerivative) perturb a MATERIAL (this OpenMC version has no cell domain): variable ∈ density/nuclide_density/temperature, `nuclide` only for nuclide_density. Derivatives are top-level `<derivative id variable material [nuclide]/>` elements in tallies.xml; the owning tally references one via a `<derivative>ID</derivative>` text sub-element (IDs auto-assigned on export). Codegen emits `openmc.TallyDerivative(variable=..., material=...)` + `tally_N.derivative = ...`; the editor is the Derivative section in the tally editor (`components/derivative-editor.tsx`).
- Kinetics (IFP) is driven by `settings.kinetics` and `src/common/kinetics-ifp.ts`: on export the three IFP tallies are auto-appended unless already present (OpenMC's own `Model.add_kinetics_parameters_tallies` pattern), `<ifp_n_generation>` is written to settings.xml, and `importXML` re-derives `settings.kinetics` from parsed IFP tallies so re-export is idempotent. Controls live in the simulation tab; IFP tallies show an 'auto' badge in the Tallies tab.
- CMFD acceleration lives in `settings.cmfd` and is **C-API-only in this OpenMC version** — there is no settings.xml element, so nothing round-trips through `importXML`; export emits `openmc.cmfd.CMFDMesh`/`CMFDRun` assignments via the pure helper `src/common/cmfd.ts` (`generateCmfdCodeLines`, kept Theia-free so vitest can import it; `OpenMCPythonExporter.generateCmfdCode` is a thin delegate). The UI is the 'Acceleration (CMFD)' block in the settings tab's Convergence section (`tabs/settings/convergence-section.tsx`); validation rules (eigenvalue-only, mesh required, inline bounds, albedo 0–1) live in `validateState`. At run time the plain `openmc` binary path cannot honor CMFD, so `SimulationRunRequest.cmfd` (resolved by `resolveCmfdRunConfig` — `meshRef` becomes inline bounds in the widget, the backend has no state) routes `startSimulation` to `startCmfdSimulation`, which spawns `python/run_cmfd.py` (mpirun-wrapped when MPI is on): the driver builds `CMFDMesh`/`CMFDRun` from the JSON config, calls `.run()` (libopenmc reads the working-directory XML), and emits one final JSON object with the statepoint path and k-eff. Depletion wins when both are configured. Generated scripts still carry the commented `# cmfd_run.run()` line for standalone use.
- The optimization parameter vocabulary (`<material>.density|temperature|<nuclide>`, `settings.*`, `geometry.<cell>.temperature`) is owned by `src/common/parameter-paths.ts` (`applyParameterByPath`). NUCLIDE-FRACTION SEMANTICS: renormalization is ELEMENT-SCOPED (enriching U235 scales only U238; compound stoichiometry like O16 is never distorted) — both `parameter-paths.ts` and `run_keff_search.py` implement it identically (`parameter-paths.test.ts`, `test_run_keff_search.py`). — sweeps (`OptimizationBackendService.applyParameterSweep`), the criticality search's 'Apply to Model', and `python/run_keff_search.py`'s `apply_search_parameter` all share those semantics; extend the vocabulary in all three places together. The optimization widget has a mode selector ('Parameter Sweep' | 'Criticality Search'); search runs go through the blocking `runKeffSearch` RPC → `OptimizationBackendService.runKeffSearch` → `python/run_keff_search.py` (process handle in `activeSearches` + `cancelKeffSearch(runId)` for the UI Stop button), which wraps `openmc.search_for_keff` (model_builder = clone base model + apply parameter; this OpenMC version requires an explicit `tol`, search.py:138).
- Depletion config persists in the custom `<depletion>` block in settings.xml (operator, solver, normalization, diff burnable mats, independent-operator file inputs, `transfer_rates`/`fission_q` as escaped JSON); the runner parses it back in `checkDepletionEnabled` and builds `run_depletion.py` args from it — extend both in lockstep. Transfer rates are applied via `Integrator.add_transfer_rate` (not on the operator). OPERATOR-MODE CONTRACT: coupled depletion is CONTINUOUS-ENERGY only (CoupledOperator needs a CE cross_sections.xml for nuclide discovery — an MG library reference crashes `DataLibrary.from_xml`); multi-group depletion = Independent operator with flux/MicroXS files (MicroXS GENERATION via get_microxs_and_flux is also CE-only — it builds per-nuclide reaction tallies); macroscopic (multigroup) materials have no nuclides and can NEVER deplete in any mode/operator. `validateState` errors on all three (macroscopic-depletable names, MG+coupled, MG+generateFromModel) plus independent-without-inputs; the driver guards macroscopic-depletables (`read_macroscopic_depletable_names` on materials.xml) then MG+coupled / MG+`--generate-microxs` (`read_energy_mode`), all BEFORE the openmc import, and wraps ALL operator-construction errors (incl. get_microxs_and_flux) as `DepletionConfigError` (a ValueError) which `main()` prints as clean JSON without a traceback; CE mode with an MG/non-XML library reference in materials.xml clears `materials.cross_sections` so `_find_cross_sections` falls back to `OPENMC_CROSS_SECTIONS` (0.15.3's CoupledOperator has no cross_sections kwarg). SOLVER CONTRACT: the 8 canonical solver ids are the `integrator_by_name` keys (`cecm`, `predictor`, `cf4`, `celi`, `epc_rk4`, `leqi`, `si_celi`, `si_leqi` — openmc/deplete/integrators.py:565-574, identical in 0.15.3 and dev); `src/common/depletion-solvers.ts` is the single source for the id/className/label list + `DEPLETION_SOLVER_ALIASES` (leapfrog→leqi, predictor-corrector→predictor, si-rk4→si_celi, plus pre-fix driver ids epc/cecmr/epcr/si-cesc) — every read path (UI select, runner parse, XML emission, python exporter) resolves through `resolveDepletionSolver`; `run_depletion.py` mirrors the same map + aliases (deprecation warning, not error).
- Materials may carry `macroscopic: { name }` (multigroup XS data, no nuclide decomposition); materials.xml uses the real `<macroscopic name="..."/>` form and round-trips. NCrystal import goes through `python/ncrystal_import.py`; `ncrystal` is an optional package in `packages.json` (`required: false`), and the materials tab disables the action with a tooltip when it is unavailable.
- Plot configs (`OpenMCPlotConfig`) cover slice, voxel, solid-raytrace, and wireframe-raytrace; `plots.xml` uses the real OpenMC element format (2-value `width` for slice, center-origin + 3-value `width` for voxel, camera/light/wireframe elements for ray-trace) and round-trips through `importXML`. The `up` vector is Python-API-only and intentionally not round-tripped.
- `volume-calc` and `native-plotting` are dedicated windows (WidgetFactory + `OpenMCViewCommands` + Advanced menu); their Python jobs run through `OpenMCRunnerService.executePythonScriptJson`. Voxel `.h5` output is converted to `.vti` by `generate_plots.py` and opened via `OpenerService` (nuke-visualizer's viewer registry claims it) — never render 3D here.
- Geometry bounding-box logic is shared in `src/common/geometry-bounds.ts` (settings tab, entropy mesh, volume-calc widget, random ray source-domain checks).
- Python services stream progress/logs back over stdout; keep output machine-parseable where the TS side consumes it.
- Live 3D previews reuse `nuke-visualizer` services — do not duplicate visualization infrastructure here.
- PREFERENCE AUDIT (P9C): only ONE widget value was promoted to a preference — `openmcStudio.lastMgxsWorkDir` (the MG conversion form's working directory, seeded on first render and saved on run, following the `nuke.endfLibrary` pattern via raw `PreferenceService`; the typed `OpenMCStudioPreferences` proxy lacks `set` in this Theia version). Deliberately SESSION-SCOPED (widget fields, reset on IDE restart, because they are per-model choices or one-off tool invocations rather than durable user defaults): MGXS generator form values (method/groups/particles/correction/temperatures — the window is a singleton and the same form now lives in the conversion section), volume-calc samples, chain-builder inputs (mode/source/nuclides/output), MG conversion method/groups/particles. Sweep drafts, depletion config, and plot configs are already project state; faceting tolerance was already a preference.

- Project-relative asset paths: `dagmcFile` and `dagmcInfo.filePath` are saved relative to the `.nuke-openmc` project file and resolved against the project directory at load, XML generation, and run time. `mgxsLibrary` is resolved the same way when it is a relative path. The `XMLGenerationRequest` carries an explicit `projectDirectory` field so the backend can resolve these assets without copying them into the output folder.
