# Nuke Visualizer

## Purpose

Plugin-based visualization framework for NukeIDE: shared infrastructure (Python environment detection, server lifecycle, widget management, health checks, output streaming) plus domain plugins for 3D/2D nuclear data (Base Visualizer for meshes/DAGMC, OpenMC for statepoints/tallies/geometry).

## Ownership

All files under `extensions/nuke-visualizer/` except generated artifacts (`lib/`, `node_modules/`, `*.tsbuildinfo`, `__pycache__`).

## Local Contracts

- TypeScript side follows `extensions/AGENTS.md`: `src/browser/`, `src/common/`, `src/node/`, wired by `visualizer-frontend-module.ts` / `visualizer-backend-module.ts`.
- Python backend lives in `python/` and is **not pip-installed**; the IDE spawns it as a subprocess:
  - `python/server.py` — CLI entry point; commands are invoked as `python server.py <plugin>.<command> --file <path>` (e.g. `dagmc.info`).
  - `python/nuke_viz/` — framework package: `plugin.py` (`@command`/`@arg` decorators, the global command registry, and `load_command_modules` — plugin loaders call it so a module that fails to import (missing optional dep) is skipped and logged via `nuke_viz.logging.info`, never raw-printed to stderr), `registry.py` (plugin registry), `logging.py`.
  - `python/plugins/base/` — Base Visualizer plugin (`commands/`: convert, dagmc, exodus; `lib/`: stdlib-only common helpers (ports, color math, camera math), dagmc, exodus_series, step).
  - `python/plugins/openmc/` — OpenMC plugin (`commands/`: statepoint, tally_viz, tally_vtk, xs_plot, geometry, materials, depletion, spectrum, basic, tracks, collision_track, weight_windows, kinetics, particle_restart, nuclear_data, ncrystal_data, endf_data, output_vtk; `lib/`: parsers, VTK export, overlap, `output_readers.py` shared HDF5 output readers, `output_vtk.py` output→VTK converters, `tally_vtk.py` tally/source/overlay→XML-VTK converters).
- Command handlers report errors as a single JSON object `{"error": ...}` with exit code 1 — never a traceback. Base-plugin commands emit it on stderr; OpenMC-plugin commands emit it on stdout. Heavy imports stay lazy (inside the handler) so missing optional dependencies surface as clean JSON errors. The node side is **stdout-first**: `openmc-output-service.ts::executeCommandJson` parses stdout regardless of exit status and uses the payload's `error` as the thrown message (stderr — log noise like plugin-load notes — is only a fallback), so the UI always shows the genuine command error. Widgets render dependency-shaped errors as an actionable missing-dependency panel (`widgets/dependency-hints.ts::detectMissingDependencies`, pure + vitest-covered).
- `src/browser/contributions/visualizer-tools-contribution.ts` exposes Visualizer commands in the Nuke Tools sidebar (`nuke-core`) under `Visualizer` and `Visualizer > OpenMC`.
- HDF5 output readers (`plugins/openmc/lib/output_readers.py`) back the `openmc.tracks-*`, `openmc.collision-track-*`, `openmc.weight-windows`, and `openmc.kinetics` commands: pure functions returning JSON-safe dicts, raising `OutputReaderError` on failure; layouts verified against the OpenMC C++/Python writers (see the module docstring). Limits/decimation are enforced server-side.
- Output viewers render natively (three.js), never through a server: `plugins/openmc/lib/output_vtk.py` converts tracks → `.vtp` polylines, collision tracks → `.vtp` point cloud, weight windows → `.vtr` rectilinear grid (one `lower_g<i>`/`upper_g<i>` cell array per energy group; `--mesh-id` anchors multi-mesh files to a chosen mesh — windows on other meshes are skipped, and the viewer offers a mesh selector when a file has windows on multiple meshes), voxel `.h5` plots → `.vti` image data (`voxel_to_vtk`), via the `openmc.tracks-vtk` / `openmc.collision-vtk` / `openmc.weight-windows-vtk` / `openmc.voxel-vtk` commands; the frontend parses the file with `parseNativeVtk` and colors particle/energy/MT/group arrays instantly. Geometry construction is numpy-only; `vtk` imports lazily for the final write. Trame-to-frontend migration (complete): `src/browser/viewer-core/` holds the native LUT pack (6 short maps), toolbar state model, ortho toggle, and canvas-screenshot helpers, and `widgets/native-vtk-viewer-widget.tsx` (+ `widgets/native-vtk/`) is the shared native three.js viewer for the same four dataset kinds. Wiring wave (landed): the tracks, collision-track, weight-windows, and random-ray/voxel viewers extend `NativeVtkViewerWidget` (convert → `FileService.read` → `setVtkText`, instant color-by, no restart). Fallback cut (landed): the serve→iframe path is gone from `output-viewer-widget.tsx` and all four subclasses — probe failure renders an error panel pointing at the generic VTK viewer instead; the generic viewer and tree View 3D are native-first with error panels instead of a server fallback.
- Color-by uses the old `base.serve` value format (`<Solid Color|Point: name|Cell: name>`, validated against the file's arrays) but applies instantly client-side — there is no server and no restart. `openmc.vtk-info` inspects any legacy/XML VTK file (arrays, ranges, grid dims).
- DAGMC/STEP conversion libs (`plugins/base/lib/dagmc.py`, `plugins/base/lib/step.py`) follow the hardened pattern: `DagmcError`/`StepError`, `find_spec` probes + lazy loaders, validators before heavy imports, additive block meta (`groups` per volume in `get_dagmc_model_info` for the client toggle). Native DAGMC path (wired): `widgets/dagmc/` (`dagmc-multiblock.ts` `.vtm` expand incl. `.vtu` decode, `dagmc-toggle-model.ts` visibility over `dagmc.info` JSON, `dagmc-viewer-widget.tsx`) plus `src/browser/viewer-core/clip-plane.ts` (per-axis `{X,Y,Z: enabled/fraction/invert}` + `toThreePlaneParamsArray` for box-section views; header shows master toggle + X/Y/Z tabs remembering their settings). New cached `base.convert-dagmc-multiblock` backs the `.h5m` claim (score 1100 > generic 1000) with single-file fallback; headers have no Solid/Fit buttons and Map disables in Solid mode.
- Exodus time series (wired): `plugins/base/lib/exodus_series.py` (`extract_exodus_series` via guarded netCDF4 with meshio single-step fallback, decimated per-step nodes + capped per-array stats) backs new `base.exodus-series` (stderr-JSON contract) via `VisualizerBackendService.getExodusSeries()`; `openmc-exodus-viewer-contribution.ts` claims `*.e`/`*.exo*` → `ExodusTimeSliderWidget` (client step index, instant array switch, per-step three.js points with global-range LUT coloring). Optional `netCDF4`/`meshio` entries in `src/common/packages.json` match `package-registry.json`/nuke-cad spec-for-spec; missing-dep hints name both.
- Headless geometry path (wired): `plugins/openmc/lib/geometry_viz.py::extract_csg_mesh` / `extract_csg_from_openmc_model` emit numpy-only cell mesh + bbox JSON (per-cell `bbox` carries both the 6-float bounds and `min`/`max` 3-lists for the frontend; unmeshed surface types fall back to `mesh: None`), `plugins/openmc/lib/slice_viz.py` adds static `build_slice_grid` / `sample_structured_values` / `write_slice_vtp` / `extract_regular_slice` / `extract_geometry_section` / `write_section_vtp`; new `openmc.geometry-mesh` / `openmc.geometry-slice-vtk` commands expose them. Native consumers: `widgets/geometry-native/` (tolerant JSON parse, `cell:<id>` selection sync both ways, clip + toolbar reuse) and `widgets/tally-native/` (`NativeVtkViewerWidget` subclass with mesh/slice/source kind routing).
- The generic `visualizer-widget.tsx` (arbitrary VTK/DAGMC/STEP files) extends `NativeVtkViewerWidget`: datasets render natively after a `parseNativeVtk` probe covering XML (`.vtp`/`.vtr`/`.vti`/`.vtu`/`.vts`, standard connectivity+offsets form) and legacy ASCII (`.vtk` POLYDATA/UNSTRUCTURED_GRID in inline-count or VTK9 `OFFSETS`+`CONNECTIVITY` form incl. leading-zero offsets, covering STEP/gmsh, DAGMC, and FEM outputs; binary legacy is rejected with a clear error). Appended payloads decode base64 chunks split at interior padding (writers flush per array) and decompress with synchronous fflate (`inflateSync`/`unzlibSync` — never the platform `DecompressionStream`, which stalls headless shells); `DataArray` offsets accept decoded-byte positions with a validated fallback to base64 character positions (emitted by vtk 9 multiblock output). Triangle datasets render as filled DoubleSide surfaces (`buildTriangleMesh`, non-indexed corner soup so per-cell coloring stays exact) with a corner-points cloud for `points` mode; line-only data renders segments, everything else points. Reads go through `readVtkText` (`native-vtk-data.ts`), which raises Theia's `files.maxFileSizeMB` gate to a 256 MB viewer budget (`NATIVE_VTK_MAX_READ_BYTES`) — use it for every viewer file read, never bare `FileService.read`. Probe failure renders an error panel. Widget ID, open-handler claims, and DAGMC sibling logic are unchanged. The server-spawn layer is deleted (`base.serve`, `dagmc.visualize`, tally/geometry `visualize-*` commands, `startServer`/`startDagmcServer` RPC) — and the last kept slice is gone too: `openmc-geometry-3d-widget.tsx` + `visualizeGeometry` (frontend service, backend spawn, protocol entry), `visualizer-proxy-contribution.ts` (+ backend binding), `proxy-retry.ts` (+ test), and `visualizer-url.ts` (+ test) are all deleted now that openmc-studio's CSG-builder preview reroutes to `OpenMCService.openGeometryViewer` (`extractGeometryMesh` → `GeometryNativeViewerWidget.setModelFile`, the same path as tree View 3D).
- Tree View 3D is native-only: `openmc-geometry-contribution.ts::showGeometry3D` runs `extractGeometryMesh` → `GeometryNativeViewerWidget.setModelFile` (with `highlightCellId` forwarding); extraction failure surfaces an error naming the cause. `viewIn3D` delegates without duplicating the order.
- Tally viewers are native-only: `plugins/openmc/lib/tally_vtk.py` (`tally_mesh_to_vtk` → `.vti`, `source_to_vtk` → `.vtp`, `overlay_to_vtk` → `.vtp` slice/full) backs new `openmc.tally-mesh-vtk` / `openmc.source-vtk` / `openmc.overlay-vtk` commands (XML only — the native parser is XML-only; the legacy OpenMC writer path is not used); `openmc-service.ts::openTallyNativeWidget` converts → `setTallyText(kind)`, and conversion/parse failure surfaces an error instead of starting a server. All three menu flows (`VISUALIZE_TALLY` → mesh, `VISUALIZE_SOURCE` → source, `OVERLAY_TALLY_ON_GEOMETRY` → overlay/slice) reroute without contribution changes. `TallyNativeViewerWidget` is WidgetFactory-bound (no registry contribution — opened programmatically).
- DAGMC + geometry openers are bound: `openmc-dagmc-viewer-contribution.ts` claims `*.vtm` → `DagmcViewerWidget` (loads in-tab with an error panel naming the generic VTK viewer as the alternative) and `*.h5m` → instant tab with a `NukeLoadingOverlay` spinner while `base.convert-dagmc-multiblock` runs, then loads or shows the in-tab error panel (with a one-shot generic-viewer jump; the `base.convert-dagmc` single-file fallback path stays working); every DAGMC open reveals the DAGMC Outline sidebar without stealing focus (CAD `revealModelPanels` pattern: add-or-reveal, never activate). `openmc-geometry-native-contribution.ts` claims `geometry.xml` → `GeometryNativeViewerWidget` (delegates to the tree first, extraction failure surfaces an error naming the cause); the tree forwards picks to open native viewers via `forwardCellToNativeViewer`. Both widgets + contributions are DI-bound in `visualizer-frontend-module.ts`.
- The random-ray results viewer (`widgets/random-ray/random-ray-results-widget.tsx`) opens legacy random-ray `.vtk`, `.vti`, or voxel `.h5` files natively (convert → `FileService.read` → `setVtkText`), with an array quick-select bar (flux groups / source / id arrays classified by the pure, vitest-covered `random-ray-arrays.ts`) that switches color-by instantly. Random-ray `.vtk` outputs are plain `<name>.vtk` files (name comes from the plot config, see OpenMC `src/random_ray/flat_source_domain.cpp::output_to_vtk`), so they are reached via the `openmc.open-random-ray-results` command with **no** filename claim — but voxel HDF5 plots (`*voxel*.h5`, `plot_*.h5`, distinctive enough) ARE claimed by `openmc-voxel-plot-viewer-contribution.ts` and open in the same widget.
- `src/browser/output-viewer/output-viewer-registry.ts` — `OutputViewerContribution` registry mapping OpenMC output files (tracks, collision tracks, weight windows, kinetics, ...) to viewers. `VisualizerOpenHandler` and `OpenMCContribution` consult `OutputViewerRegistry.getHandlerFor()` first in `canHandle`/`open` and fall through to existing behavior when nothing matches. Register viewers with `bind(OutputViewerContribution).to(...)`; matching logic lives in the pure `selectOutputViewer` function (vitest-covered). Filename matching lives in `src/browser/output-viewer/output-file-patterns.ts` (pure, vitest-covered): `tracks(_pN)?.h5`, `collision_track(.N)?.h5`, `weight_windows.h5`, `particle_restart.h5`/`particle_N_M.h5`, `*voxel*.h5`/`plot_*.h5`, `summary.h5`, `openmc_simulation_n<N>.h5`. The last is NOT a registry viewer: depletion CoupledOperator per-step files (`write_bos_data` → `openmc.lib.statepoint_write(..., write_source=False)`) share the statepoint layout minus the source bank, so `OpenMCContribution` claims them straight into the statepoint viewer (the statepoint command already tolerates a missing `source_bank`). Registered viewers: tracks (`openmc-tracks-viewer-contribution.ts`), collision track, weight windows, voxel plot (→ random-ray widget) — each a widget under `src/browser/plugins/openmc/widgets/<feature>/` extending `widgets/output-viewer-widget.tsx` (shared native-viewer lifecycle with a drag-resizable split between the 3D view and the data panel) with backend data/conversion calls via `src/node/plugins/openmc/services/openmc-output-service.ts`. Exceptions: the particle restart viewer (`openmc-particle-restart-viewer-contribution.ts`) renders its summary/property cards directly in `widgets/particle-restart/` — scalar data with no 3D pipeline (the run-single-particle action belongs to openmc-studio); and `summary.h5` (`openmc-summary-viewer-contribution.ts`) opens the geometry hierarchy + 3D view — the backend converts it on the fly via `geometry_parser.convert_summary_to_xml` (openmc.Summary round-trip to geometry.xml/materials.xml, lazy openmc import), which `openmc.geometry` applies to any `.h5` input.
- IFP kinetics results live in ordinary `statepoint*.h5` files, so they have **no** `OutputViewerContribution` (the statepoint viewer already claims those). Instead the statepoint viewer shows a conditional 'Kinetics (IFP)' tab when any tally carries an `ifp-*` score (`kinetics-utils.ts::hasIfpTallies`, pure + vitest-covered alongside `formatUncertainty`/`kineticsToCsv`); the tab lazy-loads `openmc.kinetics` via `OpenMCService.getKineticsParameters()` and renders β_eff (total + per-group), Λ_eff, uncertainties, and CSV export with friendly empty/error states.
- The Nuclear Data browser (`widgets/nuclear-data/`, OpenMC → Materials menu) is a read-only cross_sections.xml inspector backed by `openmc.nuclear-data-library` (cheap h5py group-key reads per file — full IncidentNeutron parses of hundreds of files take minutes) and `openmc.nuclear-data-nuclide` (`IncidentNeutron.from_hdf5` detail). These two commands keep the studio-era `{"success": bool, ...}` envelope — failures print `{"success": false, "error": ...}` (still exit 1), and `openmc-output-service.ts` parses stdout regardless of exit status to surface it. The detail panel's 'Plot in XS Viewer' opens the XS plot with the nuclide pre-selected via `XSPlotWidget.selectNuclide()` (public).
- The Nuclear Data window is **tabbed** (Library | NCrystal | ENDF-disabled-stub, data-driven tab bar for the ENDF workstream). The NCrystal tab (`ncrystal-tab.tsx` + pure `ncrystal-cfg.ts` builder helpers, vitest-covered) is backed by `openmc.ncrystal-materials` (`NCrystal.datasrc.browseFiles()` or `--dir` scan), `openmc.ncrystal-info` (`createInfo`: phases/composition/temperature/density/structure), and `openmc.ncrystal-xs` (`createScatter/createAbsorption` → `crossSectionIsotropic` at log-spaced energies — numpy only, no matplotlib); cfg strings carry all parameters inline (`name;temp=300K;dcutoff=...`). `ncrystal` is an optional package in `packages.json` (`required: false`); the tab renders its error panel when it is missing. The **ENDF tab** (`endf-tab.tsx` + pure `endf-format.ts` helpers) is backed by `openmc.endf-evaluations` (directory scan: sub-libraries from `decay`/`nfy`/`sfy`/`neutrons` dirs, nuclides parsed from ZA-coded filenames — no file parsing) and `openmc.endf-detail` (dispatch on filename prefix: `dec-*` → `openmc.data.decay.Decay.from_endf` modes/half-life, `nfy-*`/`sfy-*` → `openmc.data.FissionProductYields.from_endf` top-N products per energy, `n-*` → cheap MF/MT text-record scan of the 80-char ENDF records with `REACTION_NAME` labels — a full `endf.Material` parse takes seconds and warns, so it is deliberately not used). The chosen library dir persists via the `nuke.endfLibrary` preference (registered in nuke-core): the parent widget reads it ready-gated, follows changes, and persists browse picks via `onDirChange`; a module-level variable is only the pre-ready fallback.
- Some top-level imports are deliberate dependency probes that must fail fast (e.g. `import vtk` in `plugins/base/lib/dagmc_viz.py`); they carry `# noqa: F401` — do not remove them.
- Headless rendering notes: `server.py` no longer sets any ParaView batch flag; no DISPLAY/Xvfb handling remains anywhere. See `docs/dev/python-backends.md`.
- No visualization servers remain: the `/visualizer/<port>/` reverse proxy (`src/node/visualizer-proxy-contribution.ts`), `toProxiedVisualizerUrl()`, and the 5 s ECONNREFUSED/ECONNRESET retry (`src/node/proxy-retry.ts`) are deleted with the CSG-builder kept slice (see above). All viewers read files through `FileService.read` and never touch `127.0.0.1:<port>`.
- 3D navigation is three.js OrbitControls in all native viewers (damping on, right-drag pans) via `src/browser/viewer-core/orbit-controls.ts` (`createOrbitControls` + `fitBounds` + `setViewDirection` for ISO/top/front/right + `zoomBy`, same dynamic-import style as nuke-cad; no Theia imports). Never hand-roll orbit math — the custom theta/phi implementation was removed for camera bugs.
- Viewer display settings live in the Viewer Settings sidebar (`src/browser/viewer-settings/`: pure `viewer-settings-model.ts` snapshot/patch/binding-selection/snap helpers, vitest-covered, plus a React panel bound once to the active native viewer through shell activation/change events — sticky while the panel has focus, empty state with no viewer open). The panel drives each widget's existing setters through the `ViewerSettingsHost` surface (`getViewerSettingsSnapshot`/`applyViewerSettings`, implemented by the native-VTK base — inherited by the tracks/collision/weight-windows/tally/random-ray/generic viewers — plus DAGMC, geometry-native, and Exodus; no duplicated state): Color by, Map, Shading, per-axis Clip (X/Y/Z tabs persist), measure toggle, ISO/T/F/R/X/Y/Z snaps via the orbit handle. Headers are slim (file/status + error surface); the canvas keeps only the nav cluster, gizmo, and measure annotations. `src/browser/viewer-core/shading-mode.ts` (`shaded|wireframe|points|xray` → material flags, pure + vitest-covered, plus `nextViewerShadingMode` cycling for the context menu) and `clip-plane.ts` (per-axis `{X,Y,Z: enabled/fraction/invert}` + `toThreePlaneParamsArray` for box-section views) apply via `renderer.localClippingEnabled`; both re-apply in `buildScene` like opacity. Triangle surfaces render lit (`MeshLambertMaterial` + ambient/directional lights, flat facet normals) so depth reads like the dagmc viewer.
- DAGMC volume/material/group visibility + selection lives in the DAGMC Outline sidebar (`src/browser/dagmc-outline/`: pure `dagmc-outline-model.ts` snapshot/patch/binding-selection/filter/label helpers, vitest-covered, plus a React panel bound once to the active DAGMC viewer through shell activation/change events — sticky while the panel has focus, empty state with no DAGMC viewer open, live refresh via the widget's outline-change signal). The panel drives the widget's existing toggle setters plus the widget-owned canvas selection through the `DagmcOutlineHost` surface (`getDagmcOutlineSnapshot`/`applyDagmcOutline`/`selectVolume`, reusing `dagmc-toggle-model.ts` visibility — no duplicated state): volume rows (checkbox = visibility, row click = canvas highlight sync both ways via raycast pick, collapsed `Volume <id>` labels with the material as a muted suffix, Nuke tooltips throughout, never `title=`), material/group checkbox trees, Graveyard toggle, Show all, and a search filter for 20+-volume models. Without the `dagmc.info` payload, material/group sections hide and volume rows fall back to the loaded `Volume_<id>` block names (direct volume toggles still apply); the viewer keeps only the `N of M volumes (P materials, G groups)` status line.
- Native 3D chrome comes from `nuke-essentials` (never local widgets, never nuke-cad `src/`): `ViewCube` (labeled-triad orientation cube, top-right overlay, imperative quaternion updates from the controls change hook via the shared `view-cube-math.ts`, click a knob to snap through the orbit handle, hidden with no dataset), `ViewerNavBar` (one bottom-bar variant: ISO/T/F/R + fit + zoom driving the viewer-core orbit handle), `ViewBadge` (top-left dataset pill, file name), and the converged `.nuke-viewer-status-line` muted treatment on every status/hint line (native, DAGMC, geometry-native, Exodus). The old spoke-gizmo stack (`widgets/viewer-gizmo.tsx`, `widgets/viewer-nav-cluster.tsx`, `viewer-core/orientation-gizmo.ts` + test) is deleted; overlay placement for the shared components stays in `output-viewer.css`.
- Split-panel drags (output viewers' viewer/table split, nuclear-data list/detail split) share `widgets/drag-split.ts::startSplitDrag`: direct DOM writes during the drag (no per-pixel React renders, `update()` only on mouseup) and `pointer-events: none` on iframes inside the widget for the drag's duration — an iframe swallows mouse events once the cursor crosses it and would otherwise jam the drag.
- Error paths and argument handling are covered by `tests/python/test_command_error_paths.py`; keep that contract green when adding commands.
- Tests: `tests/python/` runs from the repo root via `yarn test:python`; `conftest.py` puts `python/` on `sys.path` and isolates the global command registry between tests. `tests/e2e/` holds full-profile e2e tests (`@pytest.mark.e2e`, skip cleanly in the minimal profile; cross sections come from `OPENMC_CROSS_SECTIONS`, never machine-specific defaults).
- Python package requirements live in `src/common/packages.json` (single source for TS health checks); never inline package lists in services; keep `pydagmc`'s `pipSpec` commit-pinned. Shared packages must match nuke-core's `package-registry.json`. `vtk` (conda `vtk`) is required in the `base`, `step`, and `openmc` groups — every VTK writer depends on it since the paraview removal; `exodus` stays netCDF4/meshio-only.

## Work Guidance

- Adding a plugin: create `python/plugins/<name>/` with `commands/` and `lib/`, register it in `python/plugins/__init__.py`/registry, and add the TS-side widget/open-handler wiring in `src/`. See `docs/dev/` for the full guide.
- Adding a command to an existing plugin: add a handler in the plugin's `commands/` module using `@command`/`@arg`, keep heavy imports lazy, return JSON errors (stdout for openmc-plugin commands, stderr for base-plugin commands), and add error-path tests in `tests/python/`.
- Optional heavy dependencies (openmc, vtk, pymoab, gmsh, netCDF4, meshio) must be import-guarded; the test environment only has `pytest` + `numpy`.
- Python style: ruff (config at repo root) — width 100, double quotes.
